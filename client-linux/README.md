# OpenRWP Linux client

Command-line client for the OpenRWP custodian (Node.js 20 or newer, no dependencies). It is a demo, not
production quality. It keeps documents in one folder, saves every change as a new version in the version graph of
a Record, shows the history as an ASCII graph and creates read-only capability links for third parties.

The client imports the shared library in `../core` by relative path, so run it from a clone of the repository.

## Quick start

```bash
git clone [https://github.com/recordweb/openRWP.git](https://github.com/recordweb/openRWP.git)
cd openRWP/client-linux
node bin/openrwp.js init
```

Optional alias (adjust the path to your clone):

```bash
alias openrwp='node ~/openRWP/client-linux/bin/openrwp.js'
```

## First start: `init`

`init` creates what is missing and reuses what exists. It never overwrites a file.

1. It creates `~/.openrwp` (owner only), the author key, the device key and `config.json`. A new random namespace
   UUID is generated unless `--namespace` is given.
2. It creates the document folder.
3. It prints the three values for the administrator: namespace UUID, public author key (`z6Mk...`) and public device
   key `x`. None of them is secret.
4. It asks the custodian for a token and for a random record of the namespace, and reports the result.

| Server check | Meaning |
|---|---|
| OK | The device is registered and the namespace matches |
| Not registered yet | Send the values to the administrator (see `docs/admin-anleitung.md`), then run `init` again |
| Namespace rejected (403) | The namespace in `config.json` does not belong to this device |
| Server not reachable | Network or URL problem; `init` still completes |

Cases:

- New user: `init`, send the three values to the administrator, run `init` again, expect `OK`.
- Keys exist but there is no `config.json`: `init --namespace <uuid>`. Without the option `init` stops
  (`namespace-required`), because a new UUID would not match the registered author key.
- `config.json` exists: options such as `--label`, `--base-url` or `--docs-dir` must match it, otherwise `init`
  stops (`config-conflict`).

## Document folder

Demo scope: all documents live directly in one folder, by default `<Documents>/openRWP`. The Documents folder is
read from `~/.config/user-dirs.dirs` (for example `~/Dokumente`), with `~/Documents` as fallback. It can be changed
with `docsDir` in `config.json`.

- The folder is flat. Sub folders and symbolic links are rejected.
- Names that start with a dot are ignored (LibreOffice creates lock files like `.~lock.name.odt#`).
- One file is one Record. The file name is the key: a renamed file counts as a new file and becomes a new Record.

## Commands

| Command | Purpose |
|---|---|
| `init` | Create keys and configuration, check access |
| `push <file>` | Save the current content as a new version |
| `list` | Show the documents and their status (local, no network) |
| `graph <file> [--full]` | Show the version graph (`--full`: complete hashes) |
| `pull <file> [--version <hash>] [--force]` | Write a version of the document into the folder |
| `settings <file>` | List the capability links |
| `settings <file> --create [--days N]` | Create a read link (1-30 days, default 7) |
| `settings <file> --revoke <id>` / `--revoke-all` | Revoke one link (at least 4 characters of the id) or all links |

A file can be given as a name or as a path inside the document folder. Exit codes: 0 success, 1 error, 2 wrong usage.

### push

- A new file creates a new Record (UUIDv4 generated by the client) with a root version.
- A known file is sent as a child of the version it is based on. Before sending, the client asks the custodian for the
  heads. There must be exactly one head and it must be that version. Otherwise `push` stops with `multiple-heads` or
  `head-changed` (run `pull` first). Branches are not used in the demo.
- A file that did not change since the last push (same content hash) creates no version.
- `createdAt` and `modifiedAt` are the time of the push (change list A32).
- The file is sent as one representation: Base64 in `content`, `primary: true`, `role: source`, format from the
  extension (`.odt`, `.txt`, `.md`, `.pdf`, otherwise `application/octet-stream`). Hashes are bare hex. The
  `versionHash` covers the representations literally, including `content`.
- A request is limited to 25 MB. Base64 adds one third, so the client checks the size before sending (C29).

### list

| Status | Meaning |
|---|---|
| `untracked` | Never pushed |
| `in-sync` | Same content as at the last push or pull |
| `modified` | Changed since the last push or pull |
| `missing` | Known, but the file is gone (`pull` writes it again) |

### graph

The oldest version is on top. A chain is a plain list, indentation appears only where the graph forks.
Flags: `root`, `head` (no successor, as reported by the custodian), `local` (the version the local file is based
on) and `merge of ...`.

```text
* 69f81d97  2026-10-12T12:34:48Z  draft  (root)
|
* 7d52562c  2026-10-12T12:36:18Z  draft
|
* fc7cc496  2026-10-12T13:28:51Z  draft  (head, local)
```

### pull

- Without options it writes the content of the single head. If the record has several heads it stops and asks for
  `--version`.
- `--version <hash>` writes an older version. A unique prefix of at least 8 characters (as printed by `graph`) is
  enough. The version graph is only ever written forward: the file now counts as `modified`, and the next `push`
  adds a new version on the head.
- A file with changes that were not pushed is not overwritten (`local-changes`). `--force` overwrites it.
- Before writing, the client checks `versionHash` and all `contentHash` values with the core library. Data that does
  not match is never written (`invalid-server-data`).
- The file is written through a temporary file and `rename`. The mode of an existing file is kept, a new file gets
  644 (minus umask). A document that is open in an editor must be reloaded.

### settings (capability links)

- A capability link gives read access to the whole Record (all versions). Scope `record`, mode `read`.
- `--create` prints the URL once. It is neither stored nor logged. Treat it like a password and do not paste it
  into chats. Besides the link, the output contains a direct link to the file of the local version.
- The server replaces the whole list of links on `PUT`. The client therefore sends the existing links along and only
  the fields the schema allows.
- Invalid, expired and revoked links answer 404.

## Local files in `~/.openrwp`

| File | Content |
|---|---|
| `config.json` | `baseUrl`, `namespace`, `deviceLabel`, `docsDir` (absolute path) |
| `state.json` | Per file name: `recordId`, `head`, `contentHash` |
| `author.pem` | Author key (Ed25519, PKCS#8). Not used for signing yet |
| `device.pem` | Device key (Ed25519, PKCS#8), proves the identity with DPoP |

The directory has mode 700, files mode 600. `OPENRWP_HOME` overrides the directory (used by the tests).

```json
{
  "version": 1,
  "files": {
    "hallo.odt": { "recordId": "<uuid>", "head": "<64 hex>", "contentHash": "<64 hex>" }
  }
}
```

`head` is the version the file is based on (the last head of the custodian that the client has seen), and
`contentHash` is the hash of that content. `state.json` is only a cache. The custodian is authoritative.

## Common errors

| Code | Meaning and remedy |
|---|---|
| `not-initialised` | No `config.json` or device key, run `init` |
| `device-not-registered` | The administrator has to register the device key, or the namespace is suspended |
| `network` | Server not reachable |
| `head-changed` | The server has a newer version, run `pull` |
| `multiple-heads` | The record has several heads, the demo supports one head only |
| `local-changes` | `pull` would overwrite unpushed changes, push first or use `--force` |
| `record-missing` | The server does not know the record, remove the entry in `state.json` to push the file as a new record |
| `file-too-large` | The request would exceed 25 MB |
| `outside-docs-dir` / `invalid-file-name` | Only files directly in the document folder, no hidden names |
| `invalid-server-data` | A version does not match its hashes, nothing was written |

Errors of the custodian are shown with their code and the HTTP status, for example `unknown-parent (HTTP 409)`.

## Code structure

The logic lives in `lib/` and returns plain data. `bin/openrwp.js` only reads arguments and prints. A later file
system view (FUSE) can use `lib/` unchanged.

| File | Content |
|---|---|
| `lib/api.js` | HTTP client with token cache and a fresh DPoP proof per request |
| `lib/config.js`, `lib/state.js`, `lib/paths.js`, `lib/fsutil.js` | Configuration, state, paths, atomic writes |
| `lib/documents.js` | Reading files, representation and version building |
| `lib/init.js`, `lib/push.js`, `lib/pull.js`, `lib/list.js` | Commands |
| `lib/history.js`, `lib/graph-ascii.js` | Version graph |
| `lib/settings.js` | Capability links |

## Tests

```bash
cd client-linux && npm test
```

74 tests with `node:test`. They run against a fake custodian in `testlib/` that checks real DPoP proofs (method, URL,
token hash, replay), validates versions with the core library and keeps a small version graph. The test vectors of the
change list (A13) are checked end to end. The client tests are not part of the Docker build of the server.

## Limits of this demo

- Flat document folder, one file is one Record, the file name is the key.
- One head only, no branches, no merge versions.
- Drafts only, no finalisation, no signature, no `ref` representations.
- `createdAt` equals `modifiedAt`. Files are handled in memory, one request is limited to 25 MB.
- Ed25519 only. No `watch`, no `verify`, no `sync`. A device cannot list the records of its namespace (C30).
- Namespaces and devices are registered by the administrator. There is no self-enrolment.
